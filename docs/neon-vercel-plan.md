# Plan: Accounts on Vercel + Neon

**Status: plan, being compared with [cloudflare-plan.md](cloudflare-plan.md).** Same goal: sign in, and My designs, pins and My beads are kept in a database and follow you to any device. Signed out, everything works as it does today.

## The stack

| Piece | Choice | Why |
|---|---|---|
| Site | **Vercel**, as today (the Vite `dist/`) | Nothing moves. The address stays `bead-model.vercel.app`, so the designs already in people's browsers are still there to upload on first sign-in. |
| API | **Vercel Functions** (Node), one catch-all `api/[...route].ts` with [Hono](https://hono.dev) | Works with a plain Vite site (it doesn't need Next.js). It is on the same origin as the pages, so the session cookie just works. Node has no 10 ms CPU limit. |
| Database | **Neon** Postgres, free plan, in the region nearest the Vercel functions (e.g. Singapore) | Real Postgres, scales to zero when idle and wakes up by itself. The Supabase schema carries over almost unchanged. |
| Driver | `@neondatabase/serverless` (Pool) | Made for serverless, and it also works as a `pg` pool for Better Auth. |
| Sign-in | **[Better Auth](https://better-auth.com)** running in our function, with tables in Neon. Google and GitHub to start; **email + password is possible** | Same library as the Cloudflare plan, but Node functions have the CPU for proper password hashing. |
| Email | Magic links and password reset through Resend (free tier) | Only needed for email sign-in. |

**An option to check first: Neon's Managed Better Auth.** Neon now hosts Better Auth for you (free up to 60,000 monthly active users, with email/password, OAuth, magic links and OTP), keeping users in our Neon database. That could replace running Better Auth ourselves. Two caveats: its built-in email sender is for development only, so production still needs our own SMTP (e.g. Resend), and we'd need to confirm how a Vite site (not Next.js) and our functions check its sessions. The plan below runs Better Auth ourselves, which is well-trodden and easy to move later. Switching to Managed changes only Phase 1.

## Free limits, and what they mean here

Figures are from 2026 write-ups and Vercel's limits page. Check the official pricing pages before relying on them.

| Limit | Amount | Used by |
|---|---|---|
| **Neon** storage | 0.5 GB per project (one late-2026 report says raised to 1 GB) | About 15,000 designs at 30 kB each. |
| Neon compute | 100 CU-hours a month per project, sleeps after 5 min idle | Only while queries run. A small site sleeps most of the day. |
| Neon data transfer | 5 GB a month | Design YAML going out. About 170,000 design loads. |
| Neon restore window | 6 hours (instant restore) | Plus a `pg_dump` now and then (e.g. a weekly GitHub Action). |
| Neon branches | 10 per project | Preview deployments can each get a database branch (see Phase 0). |
| **Vercel** Hobby invocations | 1 million a month | API calls only. Pages and static files don't use them. |
| Vercel Active CPU | 4 CPU-hours a month | JSON and SQL take a few ms. Password hashing is the main user. |
| Vercel commercial use | Hobby is reportedly for non-commercial use | Fine for a hobby project. Pro is $20 a month. |

**What happens at a limit** is the main difference from Cloudflare:
- **Neon:** if a monthly limit is reached, compute stops **until next month**. The API fails, while the pages still load and the local copy keeps working.
- **Vercel Hobby:** extra usage isn't billed, but the account **may be paused**, and that takes the **whole site** down, static pages included.

At this app's size neither is close. But the failure is monthly and site-wide, where Cloudflare's is daily and API-only.

**Cold starts:** after 5 minutes idle, the first query wakes Neon, which adds a few hundred ms. Local-first saving (Phase 3) hides this, because the page never waits for the server to show or save a design.

## Repository layout

```
api/
  [...route].ts     Vercel Function entry: hands every /api/* request to Hono
server/
  app.ts            Hono app: /api/auth/* → Better Auth, the rest → routes
  auth.ts           Better Auth with the Neon pool
  db.ts             the pool, and every SQL query, each filtered by the signed-in user's id
  routes/designs.ts, pins.ts, beads.ts, me.ts, import.ts
db/
  migrations/0001_auth.sql   Better Auth's tables (generated by its CLI)
  migrations/0002_app.sql    profiles, designs, pins, owned_beads
  migrate.ts                 applies new .sql files in order, tracking them in a schema_migrations table
vercel.json         build command, output dist/, function region
test/server/        API tests against a Neon branch (or local Postgres)
web/
  auth-client.ts    sign in / out / current user
  designs-store.ts, my-beads-store.ts   become local + remote (Phase 3)
```

As in the Cloudflare plan, `src/` doesn't change, and the server reuses `src/collection/*` to check incoming data.

Environment variables (in Vercel, and in `.env.local` for dev): `DATABASE_URL` (the Neon **pooled** connection string), `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID/SECRET`, `GITHUB_CLIENT_ID/SECRET`, and later `RESEND_API_KEY`. Only the server reads them. None start with `VITE_`, so none reach the browser.

## Schema (Postgres)

This is [`supabase/migrations/0001_accounts.sql`](../supabase/migrations/0001_accounts.sql) with three changes:

1. References go to Better Auth's `"user"(id)` (text) instead of `auth.users(id)` (uuid). So `owner_id` is `text`.
2. **No row level security policies.** `auth.uid()` is Supabase-only, and the database is reached only through our functions. Access control lives in `server/db.ts`, as below.
3. No `handle_new_user` trigger. The profile row is made on the first `/api/me`.

The rest stays: `designs` (uuid id, `local_id`, `kind`, `title`, `yaml`, `is_public`, `timestamptz` times, `unique (owner_id, local_id)`), `pins` keyed `(owner_id, target)`, `owned_beads` keyed `(owner_id, bead_key)`, the size checks, and the `touch_updated_at` trigger. The reasons are in [accounts-and-database.md](accounts-and-database.md#schema).

### Access control lives in the API

The database password is only on the server. **Every query goes through `server/db.ts`, and every query there takes the user id from the Better Auth session, never from the request.** It is `WHERE owner_id = $1` on reads, updates and deletes alike. Tests sign in as user A and check that user B's rows can't be read, changed or deleted.

(Neon can also do row level security with a Data API that the browser calls directly, like Supabase. It would mean less API code, but more moving parts to learn. It's not needed at this size.)

Other guards are the same as the Cloudflare plan: `HttpOnly; Secure; SameSite=Lax` cookies, an `Origin` check on requests that change data, a 1 MB body cap, and Better Auth's own rate limiting on sign-in.

## API

The same as in [cloudflare-plan.md](cloudflare-plan.md#api): `/api/auth/*`, `GET/PATCH /api/me`, `GET /api/designs?since=`, `GET/PUT/DELETE /api/designs/:id` (the newer `updated` wins, and an older one gets `409`), pins, beads, and `POST /api/import` (one transaction, upserts, safe to run twice). Writing the routes in Hono keeps them portable: the same `server/app.ts` could run on Cloudflare later with a different entry file.

## Phases

### Phase 0: database and preview branches

1. Create a Neon project in the same region as the Vercel functions. Set the function region in `vercel.json`.
2. Add the **Neon integration in the Vercel dashboard**. It sets `DATABASE_URL` and can give each preview deployment its own database branch, so pull requests can't touch production data. Watch the 10-branch limit and turn on deleting branches when previews go.
3. Add `db/migrate.ts`, and run it in the Vercel build (`npm run migrate && npm run build`), so each deploy brings its database up to date.

Done when a preview deployment builds against its own Neon branch.

### Phase 1: sign-in

1. Add `api/[...route].ts`, `server/app.ts` and `server/auth.ts` (Better Auth with the Neon pool, Google + GitHub). Generate `0001_auth.sql` with the Better Auth CLI.
2. Create OAuth apps with callback URLs for `bead-model.vercel.app`, previews (or use the production URL for previews), and `http://localhost:3000` (where `vercel dev` serves).
3. Add a sign-in button and avatar menu in `web/nav.ts`, and `web/auth-client.ts`.
4. Local dev: `vercel dev` runs Vite and the functions together, with `.env.local` pointing at a Neon dev branch.

Done when you can sign in and out with Google and GitHub, locally and on a preview, and `/api/me` returns you.

### Phase 2: data API

1. Add `0002_app.sql`, `server/db.ts` and the routes, checking input with the `src/collection/*` readers.
2. Write tests with Vitest against a throwaway Neon branch (or Postgres in Docker). These cover the owner checks, "newer `updated` wins", and an import run twice that leaves no copies.

### Phase 3: the app uses it

The same as Cloudflare Phase 3: async stores, localStorage as the working copy, debounced push with a retry queue, pull `?since=` on load and focus, an upload offer on first sign-in, and clearing the account's data from the browser on sign-out (ask first). Then update [my-designs.md](my-designs.md) and [my-beads-storage.md](my-beads-storage.md).

**No Phase 4.** The site doesn't move, so there are no redirects and no "we moved" page.

### Later

- Email sign-in: magic link or email + password, with reset emails, through Resend.
- A shared feed (`is_public`, `GET /api/feed`).
- A weekly `pg_dump` GitHub Action, since the free restore window is only 6 hours.
- If it outgrows the free plans: Neon Launch is pay-as-you-go, and Vercel Pro is $20 a month.

## Neon + Vercel vs Cloudflare

| | Vercel + Neon | Cloudflare Workers + D1 |
|---|---|---|
| Moving the site | None. Existing browser data stays reachable. | Move to a new address. People must upload or back up from the old site. |
| Database | Postgres (rich SQL, JSON, full-text search later) | SQLite (simpler, fewer features) |
| Passwords | Possible now (Node CPU) | Needs the $5/month plan |
| Idle | Neon sleeps, first request waits a few hundred ms | Always warm |
| At a free limit | Monthly. Neon stops the API until next month; Vercel may pause the **whole site**. | Daily, API only. Resets at 00:00 UTC. |
| Free headroom | 0.5–1 GB, 1M function calls a month | 5 GB, 100k API requests a day |
| Backups (free) | 6-hour restore + your own dumps | 7-day Time Travel |
| Preview data | A database branch per preview (built in) | Shares one database unless set up separately |
| Commercial use (free plan) | Vercel Hobby: reportedly not allowed | Allowed |
| Vendors | Two (Vercel, Neon) | One |

**In short:** Vercel + Neon is the easier path *from where the app is today*. There's no move, it's Postgres, and passwords are possible. Cloudflare has more free headroom, is more forgiving at its limits, and allows commercial use. For a hobby app with modest traffic, Vercel + Neon gets accounts working sooner. If it may become commercial or grow large, Cloudflare is the safer long-term free home.
